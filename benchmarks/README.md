# Governor vs Caveman Performance Benchmark

Use this when you want measured evidence instead of plugin marketing claims.
The goal is to compare quota burn and context growth for the same tasks under
the same conditions.

## Conditions

Run each task under these conditions:

1. `control`: no Caveman, no Governor.
2. `caveman`: Caveman enabled exactly as a normal user would use it.
3. `governor-hooks`: Governor enabled, no memory compression yet.
4. `governor-compressed`: Governor enabled after `/governor:compress CLAUDE.md`.
5. `governor-strict`: optional; Governor plus `/governor:strict` for broad tasks.

This separation matters. Caveman should mostly win on assistant output brevity.
Governor should win when context hygiene, tool-output filtering, planning, and
retry reduction matter.

## Required Controls

- Use the same machine, repo commit, Claude Code version, model, and plan tier.
- Use a fresh Claude Code session for each run.
- Run `/clear` or start a new session between conditions.
- Use the exact prompt text from `tasks.json`.
- Do not let one condition see fixes or notes generated by another condition.
- Run each task at least three times per condition if you want publishable
  numbers.

## What To Record

Fill one row in `run-sheet.csv` for every task/run/condition.

Required columns:

- `task_id`
- `condition`
- `run`
- `model`
- `repo_commit`
- `start_context_pct`
- `peak_context_pct`
- `end_context_pct`
- `start_5h_pct`
- `end_5h_pct`
- `assistant_output_tokens_est`
- `failed_tool_calls`
- `compactions`
- `wall_minutes`
- `task_success`

Governor-specific columns:

- `tool_output_tokens_blocked_est`: from `/governor:status`.
- `memory_original_tokens`: from `/governor:compress` result.
- `memory_compressed_tokens`: from `/governor:compress` result.

Optional columns:

- `start_7d_pct`
- `end_7d_pct`
- `notes`

## How To Run

For each task in `tasks.json`:

1. Reset to the same repo commit.
2. Start a clean session.
3. Record starting context and usage percentages from Claude Code statusline or
   usage UI.
4. Paste the exact task prompt.
5. Let the agent complete or stop when it clearly fails.
6. Record peak/end context, five-hour usage delta, failures, compactions, wall
   time, and whether acceptance criteria passed.
7. For Governor runs, run `/governor:status` and copy blocked-token totals.

Then summarize:

```bash
python3 scripts/compare_benchmarks.py benchmarks/run-sheet.csv
```

## Interpreting Results

Use these as primary metrics:

- `five_hour_delta_pct`: real Max-plan burn. Lower is better.
- `peak_context_pct`: risk of compaction and 1M-context bloat. Lower is better.
- `assistant_output_tokens_est`: where Caveman should be strongest.
- `tool_output_tokens_blocked_est`: Governor-specific tool-noise savings.
- `failed_tool_calls`: retry-loop waste. Lower is better.
- `compactions`: fewer means longer useful sessions.
- `task_success`: must stay equal or improve. Smaller answers are not a win if
  task quality falls.

Report Governor honestly:

- Memory compression savings are recurring context savings.
- Tool filtering savings apply only when commands produce noisy output.
- Prompt caching can reduce usage/cost but does not necessarily reduce context
  window occupancy.
- Planning/drift guard savings are task-dependent and should be measured as
  fewer failed loops, fewer broad scans, and fewer unplanned edits.
